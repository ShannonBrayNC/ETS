# ETS Core C2 — Evidence Object v1 Normative Contract

Status: proposed engineering specification
Profile: `ets.evidence-object.v1`
Hash profile: `ets.evidence-object.hash.sha256.v1`

## Purpose

Evidence Object v1 is the portable semantic object consumed by ETS Core, Edge, Cloud, SDKs, and independent implementations. It is additive to `EvidenceEvent`; it does not rewrite historical logs or alter the alpha Merkle profile.

## Normative object classes

An Evidence Object contains:

1. identity and schema/profile identifiers;
2. one or more claims or assertions;
3. provenance identifying source agents, activities, systems, and transformations;
4. event and decision context;
5. integrity bindings and content digests;
6. typed relationships;
7. verification records;
8. privacy and retention directives;
9. lifecycle, correction, and supersession records;
10. controlled extensions.

## Immutability boundary

The canonical object body is immutable after its object hash is computed. Verification, review, lifecycle, correction, and supersession facts are append-only records that reference the immutable object identity. A correction creates a new object and links to the corrected object; it never mutates the original hash preimage.

## Required identifiers

- `schema_id`: `ets.evidence-object.v1`
- `object_id`: globally unique stable identifier
- `object_type`: controlled type identifier
- `created_at`: UTC timestamp
- `hash_profile`: `ets.evidence-object.hash.sha256.v1`

Identifiers are case-sensitive UTF-8 strings. Implementations must not normalize identifiers beyond validation explicitly defined by the schema.

## Canonical hash preimage

Included:

- immutable identity fields;
- claims and assertions;
- provenance supplied with the object;
- context;
- relationships declared at creation;
- integrity bindings;
- privacy classification and retention intent;
- correction/supersession references declared by this object;
- extension values under registered extension namespaces.

Excluded:

- transport headers and receipts;
- database keys and append indexes;
- ingestion timestamps generated by a server;
- synchronization acknowledgements;
- tenant billing or entitlement fields;
- UI state;
- verification results generated after object creation;
- review decisions generated after object creation;
- cache, pagination, and telemetry fields.

The preimage is canonicalized using `ets.canonical.json.v1`, then hashed with SHA-256. The hexadecimal digest is lowercase and exactly 64 characters.

## Claims and assertions

A claim states a proposition. An assertion associates a claim with an asserting agent, source, method, time, and optional confidence representation. Confidence is contextual metadata and does not alter cryptographic validity.

## Provenance

Provenance must preserve the distinction among:

- original source observation;
- copied or transported representation;
- normalized representation;
- derived analysis;
- human review;
- machine-generated inference.

Transformations must identify their input references and transformation profile. Derived output must never be represented as original source evidence.

## Relationships

Core relationship types include:

- `derived_from`
- `supports`
- `contradicts`
- `corroborates`
- `corrects`
- `supersedes`
- `duplicates`
- `references`
- `part_of`

Relationship existence does not prove the semantic truth of either object. Graph persistence and confidence propagation are outside v1.

## Verification records

Verification records are append-only observations about an object or binding. They identify verifier, verification profile, time, status, reason code, and referenced inputs. They are excluded from the original object hash unless embedded as source-provided immutable assertions at creation.

## Privacy and retention

Privacy classification and retention intent travel with the object. They do not by themselves enforce access, deletion, jurisdiction, or legal-hold behavior; those remain product and deployment responsibilities.

## Extensions

Unknown fields in the normative core are rejected. Extensions must appear under `extensions`, use a collision-resistant namespace, and declare whether their values are included in the object hash. Unregistered extensions are preserved but must not silently change normative interpretation.

## Non-goals

Evidence Object v1 does not define:

- a graph database;
- policy-bound trust evaluation;
- legal admissibility;
- source completeness;
- cloud synchronization transport;
- billing, tenancy, or portal behavior;
- mutable document editing.
