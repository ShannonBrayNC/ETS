# TypeScript / Node Application SDK: task guide and quickstart

Package: `@lanternprotocol/ets-sdk` `0.1.0-alpha.1`; Node `>=22.14.0`.
Contract: `ets.application.sdk.v1`; REST `v1`. Current implementation is documented
from [client.ts](../../sdk/typescript/src/client.ts), not from hypothetical methods.
This guide covers Node use. TypeScript source alone does not establish browser,
CORS, mobile, worker or bundler qualification.

## Run the downloaded test kit first

From the extracted kit root, with supported Node already installed:

```powershell
$package = (Resolve-Path packages/typescript/lanternprotocol-ets-sdk-0.1.0-alpha.1.tgz).Path
npm --prefix examples/sdk/typescript install --ignore-scripts --no-save --package-lock=false $package
node examples/sdk/typescript/quickstart.mjs --smoke tests/fixtures/verifier/native-signed.json ./ts-bundle.json
```

Use a fresh extracted directory for each candidate. The `.mjs` sample needs no
TypeScript compiler; CI separately checks the installed package declarations.
Continue with independent verification below. Source build commands are only for
a repository checkout, not needed to consume the delivered kit.

## Consume a reviewed npm artifact

Build and pack from the repository, then install the generated tarball into the
sample (no registry publication is required):

```powershell
npm --prefix sdk/typescript install --package-lock=false
npm --prefix sdk/typescript test
New-Item -ItemType Directory -Force artifacts/typescript | Out-Null
Push-Location sdk/typescript
npm pack --pack-destination ../../artifacts/typescript
Pop-Location
$package = (Resolve-Path artifacts/typescript/lanternprotocol-ets-sdk-0.1.0-alpha.1.tgz).Path
npm --prefix examples/sdk/typescript install --ignore-scripts --no-save --package-lock=false $package
node examples/sdk/typescript/quickstart.mjs --smoke tests/fixtures/verifier/native-signed.json ./ts-bundle.json
```

These commands can need network for build dependencies; they are not a claim of
first-time fully offline toolchain installation. A prebuilt reviewed tarball and
already-installed Node can run the sample without developer TypeScript tooling.
A new project should pin the reviewed version and lock its resolved dependencies.
Use a registry only after confirming the [release](RELEASE.md) is actually
published, checking the manifest/digest/provenance and approving the source.
The package-root import is `import { EtsClient } from "@lanternprotocol/ets-sdk"`;
do not import repository internals in an installed-consumer test.

The runnable [Node example](../../examples/sdk/typescript/quickstart.mjs) consumes
the package by name. It is JavaScript ESM so it runs directly while exercising the
same TypeScript-authored SDK; the package also supplies declaration files. Its
`--smoke` mode checks health, compatibility, one capture, bundle export, auth/SDK
headers, forbidden-error normalization and malformed-body handling through an
injected deterministic `fetchImpl`. It performs **no HTTP requests**. The output
is the existing signed synthetic fixture, not live service qualification or a
new proof generated by TypeScript.

Independently verify that artifact through the separate CLI:

Use the Python environment installed by the [test-kit procedure](TEST_KIT.md),
not an unrelated global executable. On macOS/Linux use `.venv/bin/python` instead.

```powershell
& ./.venv/Scripts/python.exe -I -m ets.verifier.cli offline ./ts-bundle.json `
  --trust-store tests/fixtures/verifier/native-trust.json `
  --expected-log-id ets-cli-golden-fixture --report ./ts-verification.json
```

Use a new report path. Under the explicit public fixture key, the expected result
is `valid=true` and `standing_status=checkpoint_only`, not current trust or physical
truth. The npm package does not install `ets-verify` or a native offline verifier.

The sample atomically reserves the requested output with exclusive creation before
capture, then writes through that same open handle. Existing files are never
replaced. A failure can leave an empty or incomplete reserved output: keep it for
diagnosis, do not treat it as a valid bundle, and choose a fresh path for a later
attempt. Reconcile any uncertain append before retrying; the sample deliberately
does not delete the output or repeat the write automatically.

## Live synthetic capture (a real write)

Provision an authorized test endpoint/workspace first. Supply `ETS_BASE_URL`
(HTTPS, trailing `/`, no embedded credentials/query/fragment), exactly one of
`ETS_BEARER_TOKEN` or `ETS_API_KEY`, event-body `ETS_TENANT_ID` and
`ETS_WORKSPACE_ID`, a retained `ETS_EVENT_ID`, and stable `ETS_EVENT_TIME_UTC`
(e.g. `2026-10-28T12:00:00Z`). Inject secrets from your approved configuration
mechanism, never a committed file or copied transcript.

```powershell
node examples/sdk/typescript/quickstart.mjs --live ./new-ts-bundle.json
```

The example computes the SHA-256 of exact synthetic UTF-8 content bytes. It does
not claim arbitrary ETS event-canonicalization equivalence. Production scope
headers are omitted; event body scope must still match authenticated claims.
A server-assigned producer role is required to append. The output receipt state
is only `committed_local`; exporting a bundle does not verify it.

For explicit [local Docker Dev](DEV_ENVIRONMENT.md), set `ETS_ALLOW_LOCAL_DEV=1`,
use `http://127.0.0.1:8000/`, and omit bearer authentication. Only this sample's
local mode adds development tenant/workspace headers. That endpoint returns
unsigned checkpoints; strict verifier results must remain indeterminate without
appropriate signatures/trust. Never use a development unsigned-policy success as
a production trust claim.

## Supported methods and honest limits

| Task | Current method | Result / limit |
| --- | --- | --- |
| Health and version | `health()`, `version()` | Service claims, not independent assurance |
| Compatibility | `checkCompatibility()` | Checks REST API `v1`; not full schema negotiation |
| Capture one event | `capture(event, correlationId?)` | `EventCommitReceipt`, only `committed_local` |
| Retrieve event | `getEvent(eventId)` | `Promise<unknown>`; caller validates shape before using fields |
| Retrieve bundle | `getBundle(eventId)` | `Promise<unknown>`; export then independently verify |
| Inclusion proof | `getInclusionProof(eventId)` | Unverified JSON |
| Consistency proof | `getConsistencyProof(fromSize, toSize?)` | Unverified JSON; use safe-integer tree sizes |
| List/pagination or atomic batch | **Not provided** | Do not invent `listEvents` or `batchCapture` |
| Native strict verification | **Not provided** | Use exported bundle + shared `ets-verify` |
| Retry/idempotency-key policy | **Not provided** | No automatic retries; correlation IDs are not deduplication keys |
| Timeout/cancellation argument | **Not provided** | Inject an application-owned `fetchImpl`; methods do not accept `signal` |

Typed imports for an application:

```typescript
import { EtsClient, EtsApplicationError } from "@lanternprotocol/ets-sdk";
import type { EventCommitReceipt } from "@lanternprotocol/ets-sdk";

const receipt: EventCommitReceipt = await ets.capture(event, correlationId);
if (receipt.commitment_state !== "committed_local") throw new Error("Unexpected receipt");
const bundle: unknown = await ets.getBundle(receipt.event_id);
// Save using a new path; send serialized bytes to the shared verifier before trusting them.
```

Return types are not a runtime validator: several methods cast decoded JSON.
Validate untrusted shapes, bounded sizes, safe integer ranges and expected schema
IDs. A forged `verification_result` inside a bundle is not its verified outcome.
Keep `ets.proof_bundle.v1` and strict CLI/report contracts separate from the SDK
package version; see [compatibility](COMPATIBILITY.md).

## Transport policy and secrets

`EtsClientOptions` supports `baseUrl`, `apiKey` or `bearerToken`, development
`tenantId`/`workspaceId`, `allowInsecureLoopbackHttp`, and `fetchImpl`. Bearer tokens
cannot be combined with scope headers. The client requests `redirect: "error"`;
custom transports must preserve the intended origin, headers and redirect policy.
Prefer root endpoint URLs with a trailing slash: JavaScript URL resolution is
relative, and a non-trailing-slash path can change the destination route.

The complete example supplies an **application-level** `fetchImpl` with a 10-second
abort deadline, caller interruption and a 4 MiB streamed response cap. These are
example controls, not built-in SDK guarantees. A rejected body read or timeout
can leave an append outcome uncertain. Avoid reusing mutable credential/options
objects across tenants; the current client retains the options object supplied
at construction. Do not embed bearer/API tokens in browser-delivered code.

## Errors, retries and application batching

`EtsApplicationError` exposes `code`, optional `statusCode`, `apiCode` and
`correlationId`. Expected categories include authentication/authorization failures,
not found, conflict, validation, request too large, server error, transport error,
unsafe configuration, incompatible version and unknown error. Malformed decoded
JSON can throw a raw `SyntaxError` because JSON parsing is outside the client's
transport-error catch; handle that separately. Do not log raw response bodies,
URLs with secrets or arbitrary service-provided messages.

No automatic retry occurs. For 401/403, correct identity/role, not retry loops.
For validation or oversized input, correct the request. For 409, compare the
retained original event against a retrieved record; the conflict itself is not
an idempotent success. For network/server errors after append, reconcile the
same durable event ID and exact content/timestamp first. Never change the event
or create a new ID merely because an acknowledgement was lost.

For many events, use a bounded application queue with explicit concurrency,
backpressure and one retained result per event. `Promise.all` over arbitrary
input is not batching, transactionality or exactly-once delivery. No SDK-level
rate-limit scheduler or ordering guarantee across concurrent requests exists.
Use the Python listing surface or an explicitly reviewed API transport if event
pagination is needed; do not advertise unavailable TypeScript methods.

[Cross-language hashing vectors](CROSS_LANGUAGE.md) cover only their tested
corpus. In particular, JavaScript number precision, non-finite values, Unicode
ordering and large/nested payloads require additional qualification before
claiming client-side authoritative hashing over arbitrary industry data.
