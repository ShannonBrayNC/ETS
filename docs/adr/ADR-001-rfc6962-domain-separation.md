# ADR-001: RFC 6962 domain separation for ETS Merkle hashing

- Status: Accepted
- Date: 2026-08-01
- Decision owners: ETS protocol maintainers
- Related issue: #155

## Context

ETS had two conflicting definitions of Merkle hashing:

1. The implementation in `ets/core/merkle.py` uses RFC 6962-style domain separation.
2. The original v0.1 golden vectors used unprefixed SHA-256 concatenation.

The conflicting values were:

| Value | RFC 6962 implementation | Legacy v0.1 vector |
|---|---|---|
| Event leaf hash | `SHA256(0x00 || event_hash_bytes)` | `SHA256(event_hash_bytes)` |
| Internal node hash | `SHA256(0x01 || left_hash_bytes || right_hash_bytes)` | `SHA256(left_hash_bytes || right_hash_bytes)` |
| Two-leaf root | `a7b6a88afe611b23a8bb9836e3cd13ba706cb05d6de647d92bf05bb0aace72ee` | `8878b15a7d6a3a4f464e8f9f42591dbc0cf4bedea0ec309003d2b2ee53655ef8` |
| Event-vector leaf | `35c8cb9455f8cdfe2cdb82a2cf34e7be27012172d16358aa63245a85d269696c` | `aa78241e1e3086504c792717577120f757bd5a4b519bbc9ac7fb56881507cc14` |

Without an explicit decision, identical evidence could produce incompatible tree roots across implementations, proof bundles, SDKs, and persisted logs.

## Decision

ETS protocol vectors v0.2 and later use RFC 6962 domain separation:

```text
leaf_hash = SHA256(0x00 || event_hash_bytes)
node_hash = SHA256(0x01 || left_hash_bytes || right_hash_bytes)
empty_root = SHA256("")
```

Tree construction uses the RFC 6962 split rule: for a tree with `n > 1` leaves, split at the largest power of two strictly less than `n`. The final leaf is not duplicated for odd-sized trees.

The current implementation is authoritative and remains unchanged. The stale vectors are versioned as legacy v0.1 artifacts; v0.2 vectors are the conformance target for new implementations.

## Rationale

Domain separation prevents a serialized internal node from being interpreted as a leaf and removes structural ambiguity between leaf and node preimages. The implementation already follows this design consistently across Merkle roots, inclusion proofs, consistency proofs, and verification.

Changing the implementation to match the old vectors would weaken the protocol and invalidate the code comments, proof logic, and formal intent. Updating and versioning the vectors is the lower-risk and more secure correction.

## Compatibility

- Existing logs generated by the current implementation remain valid.
- Any external implementation built from the original v0.1 vectors is not root-compatible with ETS v0.2.
- Legacy v0.1 vectors remain available only to identify and test the historical unprefixed behavior.
- Proof bundles and tree heads must carry or be associated with a protocol/vector version before cross-system verification.
- No verifier may silently reinterpret a v0.1 root as v0.2 or vice versa.

## Migration guidance

1. Identify the hashing profile used by each persisted log.
2. Retain existing signed tree heads under their original profile.
3. Do not recompute or rewrite historical roots in place.
4. Start a new log epoch or explicitly versioned tree when moving an unprefixed implementation to v0.2.
5. Require clients and SDKs to declare support for `ets.merkle.rfc6962.v1` before accepting v0.2 proof bundles.

## Consequences

- Golden vectors now match the implementation.
- The full test suite can detect accidental removal of domain separation.
- Legacy consumers must upgrade or remain isolated to their original log epoch.
- API and proof-bundle schema versioning remains a follow-up hardening item before broad interoperability claims.
