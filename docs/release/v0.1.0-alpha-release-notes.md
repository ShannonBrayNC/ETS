# ETS v0.1.0-alpha Release Notes

Release status: **candidate**. Do not tag until PR #156 and the final freeze PR are independently approved, merged to `main`, and validated on one exact commit.

## Summary

ETS, the Evidence Transparency System, is a reference transparency-log implementation for creating verifiable receipts over evidence metadata and artifact hashes.

This alpha supports local protocol validation, API and SDK exploration, offline verification, controlled demonstrations, and limited technical pilots. It is not production trust infrastructure.

## Included

- Stable `EvidenceEvent` v1 metadata contract.
- Canonical JSON and deterministic event hashing.
- Append-only in-memory and SQLite log providers.
- Durable artifact-registry reconstruction after restart.
- RFC 6962 domain-separated Merkle profile `ets.merkle.rfc6962.v1`.
- Active v0.2 Merkle and canonical-event vectors.
- Merkle inclusion proofs and documented alpha consistency-proof behavior.
- Optional Ed25519 tree-head signing.
- Proof bundles, verifier helpers, and verification certificates.
- FastAPI API under `/api/v1` with RC compatibility routes.
- Verifier CLI and SDK helpers.
- Explorer UI reference workflow.
- Hosted JWT/JWKS profile guidance.
- Explicit runtime-profile guard that rejects the implicit all-local configuration unless deliberately authorized.
- Dependency, secret-scan, formal-method, benchmark, and six-node Docker-federation validation gates.

## Trust boundaries and non-claims

- ETS stores evidence metadata and cryptographic hashes by default, not raw evidence bytes.
- Local unsigned tree heads are not production trust anchors.
- Local header and API-key authentication modes are for development and controlled demonstrations only.
- Hosted deployments should use JWT/JWKS validation with issuer and audience checks.
- RC consistency-proof behavior is alpha behavior and must not be represented as final production-grade consistency auditing.
- SQLite is suitable for local validation, controlled demos, and limited pilots, not final horizontally scaled hosted storage.
- Production signing-key custody, rotation, revocation, and discovery require deployment-owner controls.
- Multi-tenant hosted operations, production authorization, rate limiting, SLOs, backup/restore, and disaster recovery require additional hardening.
- This release does not establish legal admissibility, regulatory compliance, truth of submitted claims, or authenticity of raw evidence.

## Protocol compatibility

The active conformance profile uses RFC 6962 domain separation:

```text
leaf_hash = SHA256(0x00 || event_hash_bytes)
node_hash = SHA256(0x01 || left_hash_bytes || right_hash_bytes)
```

The repository preserves v0.1 unprefixed vectors as a documented legacy test profile. New conformance and interoperability work should use the v0.2 vectors and `ets.merkle.rfc6962.v1` profile identifier.
